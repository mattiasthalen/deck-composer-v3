# ADR-0003 — The composer reads the whole card pool; there is no filter layer

**Status:** Accepted (2026-09-20)

## Context

`deck-composer-v2` built an uncommitted TSV of the owned collection, regenerated by
every card-data operation, with grep and awk inside the session as the filter path
(its ADR-0005). The justification was context pressure: its assumptions record
estimated the collection view would stop fitting one window at roughly five times
the collection's size.

Measured against the current collection of 603 distinct names:

| Projection | Tokens |
|---|---|
| Whole owned pool, with oracle text | 31,000 |
| Wick's colour identity slice, 332 cards | 18,000 |
| Mabel's colour identity slice, 206 cards | 11,000 |
| Gen 1's `oracle.jsonl`, whole file | 69,000 |

## Decision

**The composer receives the card facts directly.** No collection view, no query
operation, no filter path.

Rejected: v2's TSV with grep as the filter path. It re-implements grep over a file
the project controls, which is a pass-through layer, and it solves context pressure
that does not exist at this collection size. Building it now is generalization
against a requirement nobody has.

## Consequences

One fewer file to keep in step, and one fewer regeneration step in every operation
that touches card data.

The decision is size-dependent and will need revisiting at roughly five times the
current collection, when the whole pool approaches 150,000 tokens. Adding a filter
layer at that point is a local change: the composer's input narrows, and nothing
else moves.

A composer that wants a subset filters it in the session, as it would any other
data it holds.
